20. AI¶

20.1. BigQuery ML¶

BigQuery MLは、BigQuery上のデータをそのまま利用して機械学習モデルを構築・利用できるサービスである。

通常の機械学習では、データを分析基盤からPython環境へ取り出し、前処理・学習・評価・予測を行う必要がある。一方、BigQuery MLではこれらの処理をSQLのみで実行できるため、大量データを移動することなく迅速にモデルを開発できる。

特に、データ分析担当者やSQLに慣れたエンジニアが機械学習を導入しやすいよう設計されている。

20.1.1. 設計思想¶

BigQuery MLの目的は、「データウェアハウスの中で機械学習を完結させること」にある。 一般的なML開発では、データ抽出・加工・学習環境への転送など、多くの工程が必要になる。

BigQuery
    ↓
CSV出力
    ↓
Python
    ↓
前処理
    ↓
学習
    ↓
予測

BigQuery MLではこれらをBigQuery内で実行できる。

BigQuery
    ↓
CREATE MODEL
    ↓
ML.EVALUATE
    ↓
ML.PREDICT

データ移動が不要になることで、開発速度の向上や運用負荷の削減につながる。

20.1.2. モデル開発の流れ¶

BigQuery MLでは、一般的に以下の流れでモデルを利用する。

手順

内容

データ準備

BigQueryテーブルを用意する

モデル作成

CREATE MODELで学習を実施

モデル評価

ML.EVALUATEで性能を確認

予測

ML.PREDICTで推論を実施

説明

ML.EXPLAIN_PREDICTで特徴量の寄与を確認（対応モデルのみ）

SQLだけで一連の処理を完結できることが特徴である。

20.1.3. 主なモデル¶

BigQuery MLでは、多くの一般的な機械学習アルゴリズムを利用できる。

モデル

用途

線形回帰

連続値の予測

ロジスティック回帰

二値分類

Boosted Tree

分類・回帰

Random Forest

分類・回帰

DNN

分類・回帰

K-means

クラスタリング

PCA

次元削減

ARIMA_PLUS

時系列予測

Matrix Factorization

推薦システム

目的に応じて、CREATE MODEL時にモデルタイプを指定する。

20.1.4. 前処理¶

BigQuery MLでは、モデル作成時に前処理をモデルへ組み込むことができる。

TRANSFORM句を利用することで、学習時と予測時で同じ前処理が自動的に適用される。

代表的な利用例として、カテゴリ特徴量のOne-Hot Encodingがある。

TRANSFORM(
    ML.ONE_HOT_ENCODER(category)
)

前処理をSQLへ統一することで、学習時と推論時の不整合を防ぐことができる。

20.1.5. モデルの評価¶

学習したモデルはML.EVALUATEによって評価できる。

モデルの種類に応じて、Accuracy・Precision・Recall・RMSEなど適切な評価指標が自動的に出力される。

学習データだけでなく評価データに対して実行することで、汎化性能を確認できる。

20.1.6. 予測¶

学習済みモデルはML.PREDICTで利用する。

新しいデータを入力するだけで予測結果が返されるため、追加のアプリケーションコードを書く必要がない。

20.1.7. モデルの説明¶

対応するモデルではML.EXPLAIN_PREDICTを利用できる。

これは各予測について、

  • どの特徴量が予測へ影響したか

  • どの程度寄与したか

を確認できる機能であり、Explainable AIの一つである。

特に金融や医療など、予測理由の説明が必要なシステムで利用される。

20.1.8. 利用シーン¶

BigQuery MLは以下のようなケースで利用される。

  • BigQueryにデータが蓄積されている

  • SQL中心でモデルを構築したい

  • 迅速にPoCを実施したい

  • シンプルな機械学習モデルで十分である

一方で、独自アルゴリズムや複雑なディープラーニング、細かな学習制御が必要な場合はVertex AIの利用が適している。

20.2. Vertex AIによるモデル開発¶

Vertex AIは、Google Cloudで機械学習モデルの開発・管理・運用を統合的に行うためのプラットフォームである。

BigQuery MLがSQL中心の機械学習サービスであるのに対し、Vertex AIはより柔軟なモデル開発やMLOpsを実現することを目的としている。

機械学習では、モデルを作るだけではなく、データの前処理、学習、実験管理、モデル管理、デプロイまで多くの工程が存在する。Vertex AIでは、それらを一つのプラットフォーム上で管理できる。

20.2.1. 構成¶

モデル開発で利用する主要なサービスは以下で構成される。

サービス

役割

AutoML

コードを書かずにモデルを作成する

Vertex AI Pipelines

MLワークフローを自動化する

Vertex AI Experiments

実験結果やハイパーパラメータを管理する

Vertex ML Metadata

パイプラインやモデルのリネージを管理する

TensorBoard

学習中の損失や精度などを可視化する

Model Registry

学習済みモデルを管理する

これらは独立したサービスではあるが、実際の開発では組み合わせて利用することが多い。

20.2.2. モデル開発の流れ¶

一般的なモデル開発は以下のような流れになる。

データ準備
      ↓
モデル学習
      ↓
実験結果の確認
      ↓
モデル登録
      ↓
デプロイ

Vertex AIでは、それぞれの工程を専用サービスが担当する。

データ準備
      ↓
AutoML / Custom Training
      ↓
Experiments
      ↓
Model Registry
      ↓
Endpoint / Batch Prediction

また、この一連の流れ全体をPipelinesで自動化できる。

20.2.3. AutoML¶

AutoMLは、機械学習アルゴリズムやハイパーパラメータを自動的に選択し、モデルを構築するサービスである。

コードを書くことなく学習できるため、短期間でモデルを作成したい場合やPoCに適している。

一方で、独自モデルや細かな学習制御はできない。

20.2.4. Vertex AI Pipelines¶

Vertex AI Pipelinesは、機械学習ワークフローを自動化するサービスである。

前処理・学習・評価・デプロイなどを一つのパイプラインとして定義できる。

各処理はコンポーネントとして管理されるため、再利用や自動実行が容易になる。

また、パイプライン実行時にはML Metadataへ情報が自動的に記録される。

20.2.5. Vertex AI Experiments¶

Experimentsは、モデル開発時の実験結果を管理するサービスである。

主に以下の情報を保存する。

  • ハイパーパラメータ

  • 評価指標

  • 実験名

  • 実行結果

複数回学習したモデルを比較し、最も性能の良いモデルを選択する際に利用される。

20.2.6. Vertex ML Metadata¶

ML Metadataは、モデル開発の履歴を管理するサービスである。

データセット、モデル、パイプライン、予測などの関係を記録し、「どのデータからどのモデルが作られたのか」を追跡できる。

このようなデータやモデルの系統情報をリネージ（Lineage）と呼ぶ。

パイプラインを利用すると、多くの情報は自動的にMetadataへ登録される。

20.2.7. TensorBoard¶

TensorBoardは、機械学習の学習状況を可視化するツールである。

主に以下の情報をグラフとして確認できる。

  • Loss

  • Accuracy

  • Learning Rate

  • エポックごとの学習状況

ディープラーニングでは、学習が正常に進んでいるかを確認するためによく利用される。

20.2.8. Model Registry¶

Model Registryは、学習済みモデルを一元管理するサービスである。

モデル名、バージョン、説明などを管理でき、デプロイ対象となるモデルを明確に管理できる。

新しいモデルを追加しても、既存モデルは保持されるため、過去のモデルへ戻すことも容易である。

20.2.9. 設計思想¶

Vertex AIでは、それぞれのサービスが一つの役割に特化している。

  • モデルを作る

  • 実験を管理する

  • 履歴を管理する

  • モデルを管理する

これらを分離することで、大規模なチーム開発や継続的なモデル改善に対応できるよう設計されている。

また、Pipelinesを中心に各サービスを連携させることで、MLOpsを実現しやすくなっている。

20.3. モデルのデプロイ¶

機械学習モデルは、学習しただけでは利用できない。

実際のシステムで予測を行うためには、学習済みモデルをデプロイし、予測リクエストを受け付けられる状態にする必要がある。

Vertex AIでは、利用方法に応じて以下の2つの予測方法が提供されている。

方式

用途

Endpoint

リアルタイムに予測を行う（オンライン予測）

Batch Prediction

大量データをまとめて予測する（バッチ予測）

20.3.1. オンライン予測（Endpoint）¶

Endpointは、リアルタイムで予測を実行するためのサービスである。

アプリケーションからリクエストを送信すると、デプロイされたモデルが即座に推論を実行し、結果を返す。

アプリケーション
        ↓
    Endpoint
        ↓
      Model
        ↓
    Prediction

APIとして利用されるため、ユーザー操作に対して即座に結果を返す必要があるシステムで利用される。

20.3.1.1. 利用例¶

  • 商品レコメンド

  • 不正取引検知

  • ローン審査

  • チャットボット

  • リアルタイム需要予測

20.3.1.2. Endpointの特徴¶

  • 低遅延で予測できる

  • オートスケーリングに対応

  • 複数モデルを同一Endpointへデプロイできる

  • トラフィック分割による段階的なリリースが可能

20.3.2. Batch Prediction¶

Batch Predictionは、大量データを一括で予測するサービスである。

入力データをCloud StorageやBigQueryから読み込み、予測結果をCloud StorageまたはBigQueryへ出力する。

BigQuery
Cloud Storage
      ↓
Batch Prediction
      ↓
BigQuery
Cloud Storage

リアルタイム性はないが、大量データを効率的に処理できる。

20.3.2.1. 利用例¶

  • 売上予測

  • 顧客スコアリング

  • 離反予測

  • 定期レポート作成

20.3.3. EndpointとBatch Predictionの使い分け¶

両者の違いは、「いつ予測結果が必要になるか」である。

項目

Endpoint

Batch Prediction

予測タイミング

リクエスト時

一括実行

応答速度

数百ms〜数秒程度

リアルタイムではない

処理対象

少量データ

大量データ

利用方法

API経由

ジョブ実行

主な用途

Webサービス・アプリ

分析・レポート・定期処理

リアルタイム性が必要ならEndpoint、大量データをまとめて処理するならBatch Predictionを利用する。

20.3.4. モデルの更新¶

新しいモデルを学習した場合でも、既存システムへ影響を最小限にしながら切り替えることが重要になる。

Vertex AIでは、一つのEndpointに複数のモデルを配置し、それぞれへ送るトラフィックの割合を設定できる。

Endpoint
   ├── Model A（90%）
   └── Model B（10%）

これにより、新しいモデルへ少しずつリクエストを流し、安全性を確認しながら切り替えることができる。

このような運用はカナリアデプロイメントと呼ばれる。

20.3.5. オートスケーリング¶

Endpointは予測リクエスト数に応じて、自動的に推論ノードを増減できる。

アクセスが少ない時間帯はノード数を減らし、アクセスが集中した場合には自動的にスケールアウトするため、コストと性能を両立できる。

一方、急激なアクセス増加時には、新しいノードの起動時間によって一時的に応答時間が長くなる場合がある。

20.4. モデルの運用¶

機械学習モデルは、デプロイした時点が完成ではない。

現実のデータは時間とともに変化するため、モデルの精度は徐々に低下する可能性がある。そのため、本番環境ではモデルの性能や入力データを継続的に監視し、必要に応じて再学習を行うことが重要となる。

Vertex AIでは、モデル運用を支援するサービスとしてModel MonitoringやFeature Storeが提供されている。

20.4.1. Model Monitoring¶

Model Monitoringは、本番環境で利用されているモデルを継続的に監視するサービスである。

トレーニング時のデータと本番データを比較し、特徴量の分布や予測傾向に大きな変化がないかを監視できる。

異常を検知した場合には通知を行い、モデルの再学習や調査のきっかけとなる。

20.4.2. 監視対象¶

Model Monitoringでは、主に以下の情報を監視できる。

監視対象

内容

特徴量（Feature）

入力データの分布変化を監視する

特徴量の重要度（Feature Attribution）

予測に影響する特徴量の変化を監視する

特徴量の重要度を監視することで、「入力データは変わっていないが、モデルの判断基準が変化している」といった問題も検知できる。

20.4.3. ドリフト¶

モデル運用では「ドリフト」が重要な考え方となる。

ドリフトとは、学習時と本番環境でデータや予測傾向が変化する現象を指す。

代表的なものは以下である。

種類

内容

Feature Drift

入力特徴量の分布が変化する

Prediction Drift

モデルの予測結果の分布が変化する

Attribution Drift

特徴量の重要度が変化する

ドリフトが大きくなると、学習時には高かった精度が本番環境で維持できなくなる可能性がある。

20.4.4. リクエスト・レスポンスログ¶

Model Monitoringでは、Endpointのリクエスト・レスポンスログを利用して監視を行う。

そのため、Model Monitoringを利用する場合は、Endpointでリクエスト・レスポンスロギングを有効にしておく必要がある。

これらのログは、監視だけでなくモデルの再学習データとして活用されることもある。

20.4.5. Feature Store¶

Feature Storeは、特徴量を一元管理するサービスである。

機械学習では、同じ特徴量を学習時と予測時で利用することが重要となる。

Feature Storeを利用することで、特徴量の定義や管理を統一し、一貫した特徴量を利用できる。

データ
   ↓
特徴量生成
   ↓
Feature Store
   ├── 学習
   └── オンライン予測

同じ特徴量を共有することで、学習時と推論時の不整合を防ぐことができる。

20.4.6. 再学習¶

モデルはドリフトを検知したからといって、必ず再学習するわけではない。

監視結果をもとに、

  • ドリフトの大きさ

  • モデル精度

  • ビジネスへの影響

などを総合的に判断して再学習を実施する。

不要な再学習はコスト増加につながるため、適切なタイミングで実施することが重要である。

20.4.7. 運用の流れ¶

モデル運用は一般的に以下の流れとなる。

モデルをデプロイ
        ↓
リクエスト・レスポンスを記録
        ↓
Model Monitoringで監視
        ↓
ドリフトを検知
        ↓
必要に応じて再学習
        ↓
新しいモデルをデプロイ

このサイクルを継続的に回すことで、本番環境でも高い予測性能を維持できる。

20.5. Explainable AI¶

Explainable AI（XAI）は、機械学習モデルが「なぜその予測を行ったのか」を人間が理解できる形で説明するための技術である。

近年の機械学習モデル、特にディープラーニングは高い予測性能を持つ一方で、内部の判断過程が複雑であるためブラックボックスモデルと呼ばれることが多い。

Explainable AIは、このブラックボックス性を補い、モデルの予測根拠を可視化することを目的としている。

金融や医療など、予測理由の説明が求められる分野では特に重要となる。

20.5.1. 説明の種類¶

Explainable AIには、大きく分けて2種類の説明がある。

種類

説明

Global Explanation

モデル全体がどのような特徴を重視しているかを説明する

Local Explanation

個々の予測に対して、どの特徴量がどれだけ影響したかを説明する

例えば、

  • 「このモデルは年齢を重視している」はGlobal Explanation

  • 「この顧客は年収が高かったため承認された」はLocal Explanation

となる。

20.5.2. 主な説明手法¶

Google Cloudや一般的な機械学習でよく利用される説明手法は以下の3つである。

手法

主な対象

SHAP

表形式データ・ツリーモデル

Integrated Gradients

ディープラーニング

Sampled Shapley

汎用モデル（Vertex AI）

それぞれ、予測への寄与度を計算するという目的は同じだが、計算方法や得意なモデルが異なる。

20.5.3. SHAP¶

SHAP（SHapley Additive exPlanations）は、ゲーム理論のShapley値を応用した説明手法である。

各特徴量が予測結果へどれだけ貢献したかを数値として表すことができる。

ツリーベースモデルとの相性が良く、XGBoostやRandom Forestなどで広く利用されている。

一方で、特徴量数やモデル規模が大きくなると計算コストが高くなる。

20.5.4. Integrated Gradients¶

Integrated Gradientsは、ディープラーニング向けの説明手法である。

入力データから基準値までの勾配を積分することで、各入力が予測へ与えた影響を求める。

画像分類や自然言語処理など、TensorFlowを利用したニューラルネットワークで多く利用される。

画像では、「どの部分を見て犬と判断したか」といった形で可視化されることが多い。

20.5.5. Sampled Shapley¶

Sampled Shapleyは、Shapley値を近似計算するExplainable AI手法である。

すべての特徴量の組み合わせを計算する代わりにサンプリングによって近似するため、大規模モデルでも現実的な時間で説明を生成できる。

Vertex AI Explainable AIでは、この手法を利用してカスタムモデルの説明を行うことができる。

20.5.6. Vertex AI Explainable AI¶

Vertex AIではExplainable AIが統合されており、モデルをデプロイする際に説明機能を有効化できる。

予測結果と合わせて特徴量の寄与度も取得できるため、追加実装を最小限に抑えながら説明可能なモデルを構築できる。

対応する説明手法はモデルによって異なるため、利用するモデルに応じて適切な手法を選択する必要がある。

20.5.7. 手法の使い分け¶

手法

特徴

SHAP

表形式データやツリーモデルに適している

Integrated Gradients

ディープラーニングに適している

Sampled Shapley

Explainable AIでは、どの手法が優れているかではなく、モデルの種類に応じて適切な手法を選択することが重要である。

20.6. モデル評価指標¶

機械学習モデルは、学習後に性能を評価する必要がある。

単純に「正解率が高いか」だけでは、実際の業務で利用できるモデルとは限らない。

例えば、不正取引検知では正常な取引が圧倒的に多いため、すべてを「正常」と予測するだけでも高いAccuracyになる。しかし、不正取引を見逃してしまうため、このモデルは実用的ではない。

そのため、機械学習では目的に応じて適切な評価指標を選択することが重要となる。

20.6.1. 混同行列（Confusion Matrix）¶

分類モデルの評価では、まず混同行列（Confusion Matrix）の考え方を理解することが重要である。

実際＼予測

Positive

Negative

Positive

TP（True Positive）

FN（False Negative）

Negative

FP（False Positive）

TN（True Negative）

それぞれの意味は以下の通り。

用語

説明

TP

正しい陽性予測

TN

正しい陰性予測

FP

誤って陽性と予測した

FN

誤って陰性と予測した

多くの評価指標は、この4つの値から計算される。

20.6.2. Precision¶

Precision（適合率）は、予測したものの正確性（Precision）を表す。

Precision = TP / (TP + FP)

Precisionが高いほど、陽性と判断したものを誤る割合が少ない。

20.6.2.1. 重視するケース¶

誤検知（False Positive）のコストが高い場合に重視される。

例

  • スパムメール判定

  • ローン審査

  • 医療検査（不要な精密検査を減らしたい場合）

20.6.3. Recall¶

Recall（再現率）は、現実世界でどれだけ正解を回収（Recall）できたかを表す。

Recall = TP / (TP + FN)

Recallが高いほど、見逃し（False Negative）が少ない。

20.6.3.1. 重視するケース¶

見逃し（False Negative）のコストが高い場合に重視される。

例

  • がん検診

  • 不正アクセス検知

  • 故障予測

  • 災害検知

20.6.4. PrecisionとRecallの関係¶

PrecisionとRecallは、多くの場合トレードオフの関係にある。

例えば、陽性と判定する基準を緩くすると、多くの陽性を検出できるためRecallは向上するが、誤検知も増えるためPrecisionは低下する。

逆に、判定基準を厳しくするとPrecisionは向上するが、見逃しが増えるためRecallは低下する。

そのため、どちらを重視するかはビジネス要件によって決定する。

20.6.5. 閾値（Threshold）¶

分類モデルは、多くの場合「陽性である確率」を出力している。

最終的に陽性・陰性へ分類するためには、閾値（Threshold）を設定する。

予測確率
      ↓
Threshold
      ↓
Positive / Negative

一般的には0.5が利用されることが多いが、業務要件に応じて変更される。

例えば、

  • 閾値を下げる

    • Recallが向上しやすい

    • Precisionは低下しやすい

  • 閾値を上げる

    • Precisionが向上しやすい

    • Recallは低下しやすい

となる。

そのため、モデルそのものだけではなく、閾値の調整も重要なモデル改善手法の一つである。

20.6.6. 評価指標の選択¶

評価指標は、モデルの性能ではなく「ビジネスで何を重視するか」によって決まる。

重視したいこと

主な指標

誤検知を減らしたい

Precision

見逃しを減らしたい

機械学習では、最も高い指標を目指すのではなく、業務要件に適した指標を選択することが重要となる。
